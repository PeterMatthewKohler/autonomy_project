# Review of last week

## What went well

1. **You owned the substantive geometry.** The rosbag reader and deserialization were appropriately AI-scaffolded, while you filled in the consecutive-sample distance sum, the ideal route calculation, and the ratio. That is exactly the right AI-assisted split for this project.

2. **You checked the frame contract before trusting the data.** Rejecting odometry unless it reports `odom -> base_link` is a good robotics habit: validate what the numbers mean before calculating with them.

3. **You treated the surprising result as evidence.** When the ratio came out near `0.965`, you correctly reasoned that the rover can stop inside the goal-tolerance region rather than at each exact commanded point. You also identified two important limitations: a value near `1.0` does not by itself prove good control, and unreliable odometry would make the metric unreliable.

## Areas to improve

1. **The denominator is not quite a lower bound for the path actually completed.** “Path stretch” normally implies a ratio of at least `1.0`: actual path length divided by the shortest path between the same endpoints. Your denominator passes through the exact commanded goals, while the rover is allowed to stop up to `0.1 m` away from each. The `0.965` result is therefore plausible, but the metric is more precisely a **commanded-route distance ratio**. Keep the number, but name and interpret it accurately.

2. **`longitudinal_dist` is imprecise terminology.** The script sums planar displacement in the `odom` frame. “Longitudinal” usually means motion along the vehicle’s forward body axis. Rename it to something like `actual_planar_distance` so the variable records both the quantity and its frame interpretation.

3. **Sample count alone does not prove full mission coverage.** Print the first and final pose plus final error to the last goal, and retain a `COMPLETE` log or note. This gives evidence that the recording did not stop early. That level of validation is enough here; production-grade experiment infrastructure is not needed.

## What to carry forward

**A surprising metric is not automatically a software bug. First ask whether the experiment and metric compare the quantities you think they compare.**

# Week 6 — Run one controlled heading-tolerance experiment

**Generated:** October 26, 2026

## Weekly goal

Use the existing mission, bag recorder, and analysis script to compare two controller settings while changing only one variable:

- baseline: `heading_tolerance = 0.25 rad`
- treatment: `heading_tolerance = 0.10 rad`

The learning loop is:

`predict -> control variables -> run -> measure -> compare -> explain`

The goal is not to “find the best value.” It is to learn how to design a small simulation experiment that can falsify your prediction.

## Estimated time

**70–100 minutes core**, including Isaac Sim startup, ROS setup, parameter verification, recording, and normal troubleshooting.

Reuse the Week 5 bag as the baseline only if it contains the same mission, the default `0.25 rad` heading tolerance, a comparable reset pose, and the full mission. Otherwise record a fresh baseline. If two clean runs consume the session, interpretation can remain a short written note.

## Concrete tasks

### 1. Predict and define the experiment — 10 minutes

Before changing anything, write down:

- **Independent variable:** `heading_tolerance`
- **Measured output:** actual planar distance and commanded-route distance ratio
- **Held constant:** three goals, goal tolerance (`0.10 m` in the current parameter files), gains, speed limits, simulator scene, starting pose, and starting orientation

Make a directional prediction:

- Will `0.10 rad` produce more or less curved forward motion?
- Will actual planar distance increase, decrease, or remain effectively unchanged?
- Could the stricter gate make the mission take longer even if the path becomes straighter?
- Why does turning in place contribute little to X/Y path length?

Do not phrase the prediction as “the ratio will improve.” First define which physical behavior you expect to change.

### 2. Add two small trust checks to the analyzer — 15–20 minutes

Keep the current script and bag-reading scaffold. Make only these changes:

1. Rename `longitudinal_dist` to `actual_planar_distance`.
2. Print:
   - first `x, y`;
   - final `x, y`;
   - distance from the final pose to the final goal; and
   - sample count.
3. Label the existing ratio **commanded-route distance ratio**, or explicitly document why it can be below `1.0`.

A final error near or below the configured goal tolerance supports that the bag contains the end of the mission. Also retain or write down the mission node’s `COMPLETE` observation; final pose alone cannot prove that every intermediate goal was processed.

AI may handle ROS message syntax or review the edits. You should personally own what each check proves and what it cannot prove.

### 3. Record the controlled comparison — 25–35 minutes

For each run:

1. Reset Nova Carter to the same simulator pose and orientation.
2. Verify the actual parameter value before motion:

   ```bash
   ros2 param get /waypoint_node heading_tolerance
   ```

3. Run the same three-goal mission.
4. Record `/chassis/odom` and `/cmd_vel`.
5. Let the mission reach `COMPLETE`.

Use clear bag names such as:

```text
week6_heading_025
week6_heading_010
```

Change the parameter through the existing launch/config mechanism and verify it at runtime. Change nothing else. Restore the repository’s `0.25 rad` setting after the experiment.

If the original Week 5 bag is a valid baseline, record only the `0.10 rad` treatment. If the reset pose is not comparable, record both runs instead of pretending the comparison is controlled.

### 4. Measure, compare, and diagnose — 20–25 minutes

Run the same analyzer on both bags and make a tiny table containing:

| Run | Heading tolerance | Start X/Y | Actual planar distance | Commanded-route ratio | Final-goal error |
|---|---:|---|---:|---:|---:|
| Baseline | 0.25 rad | ... | ... m | ... | ... m |
| Treatment | 0.10 rad | ... | ... m | ... | ... m |

Then write 4–6 sentences answering:

- Did the observed direction match your prediction?
- Did the stricter tolerance visibly create more rotate-then-drive behavior?
- Is the distance difference large enough to distinguish from ordinary run-to-run variation?
- Did either run stop well inside or near the edge of the `0.10 m` goal tolerance?
- Why can neither one run per setting nor a ratio near `1.0` establish that one controller is generally better?
- What additional metric—mission duration, cross-track error, oscillation, or energy—might tell a different story?

It is a valid result to conclude that the difference is too small or the reset was not controlled well enough. Good experiments can be inconclusive.

## AI-use boundary

Healthy AI assistance includes:

- rosbag and deserialization boilerplate;
- parameter/launch troubleshooting;
- producing the Markdown table;
- reviewing the analyzer for implementation errors;
- helping inspect a runtime failure.

You should personally own:

- the hypothesis;
- independent versus controlled variables;
- frame and unit reasoning;
- why the metric can fall below `1.0`;
- whether the comparison is valid;
- the engineering conclusion and its uncertainty.

Do not ask AI whether `0.10` is “better” before you have written your own interpretation from the evidence.

## What not to do

- No gain tuning.
- No search across many parameter values.
- No controller refactor.
- No new ROS package or interface.
- No action-server migration.
- No retry/preemption cleanup.
- No mapping, planning, or obstacle avoidance.
- No statistical benchmark suite.
- No simultaneous change to goal tolerance, speeds, gains, goals, or starting pose.
- No permanent change to the default parameter merely because one run looked better.
