# Week 8 — Dead-reckon heading from the IMU

**Generated:** November 9, 2026

## Weekly goal

Integrate `/chassis/imu` angular velocity over one controlled planar turn to produce a dead-reckoned heading, then compare the result with odometry over the same time interval.

This is the smallest useful bridge from sensor characterization toward state estimation:

`predict -> verify frames and data -> integrate gyro rate -> compare with odometry -> diagnose error -> explain`

You are not building a filter yet. The purpose is to see exactly what open-loop propagation does, where time enters the equation, and why even a small rate bias eventually becomes a heading error.

## Estimated time

**65–90 minutes core**, including Isaac Sim and ROS startup, verifying or replacing one bag, implementation, debugging, and writing down the measured result.

Stop after the core comparison if you reach 90 minutes. The optional bias correction is useful, but completing one traceable raw-integration result is more important.

## Concrete tasks

### 1. Predict the result and verify the frame relationship — 10–15 minutes

Before running the analyzer, write down:

- the approximate commanded turn rate and duration;
- the expected sign and approximate total heading change, using `delta_yaw ≈ angular_rate * duration`;
- whether you expect raw integrated IMU heading to finish ahead of or behind odometry; if you cannot predict the direction from the measured stationary bias, explicitly predict only that the error will be nonzero; and
- what error growth you would expect from a constant gyro bias `b` over elapsed time `T`: `heading_error ≈ b * T`.

Then verify the relevant frames:

```bash
ros2 topic echo /chassis/imu --once
ros2 topic echo /chassis/odom --once
ros2 run tf2_ros tf2_echo base_link chassis_imu
```

Confirm that:

- IMU angular velocity is in `chassis_imu` and uses `rad/s`;
- odometry pose is in `odom`, with the child frame reported by the message; and
- `chassis_imu` has the expected orientation relative to `base_link`, especially the direction of its z-axis.

If `tf2_echo` cannot find the transform, document that fact and inspect the Isaac Sim sensor mounting or TF tree. Do not silently rename the IMU frame to `odom` in the analysis.

### 2. Verify or record one valid turn bag — 10–20 minutes

First inspect the local positive-yaw recording:

```bash
ros2 bag info <positive-yaw-bag>
```

Reuse it only if it contains nonzero message counts for both:

- `/chassis/imu`; and
- `/chassis/odom`.

If it does not, record one replacement bag. Keep the motion simple: begin stationary, command approximately `+0.3 rad/s` with zero linear velocity for about 3–5 seconds, stop, and leave a brief stationary margin at both ends. Check `/cmd_vel` publishers before commanding motion and send an explicit zero command afterward.

Run `ros2 bag info` on the replacement and save or transcribe the two topic counts and recording duration. Do not add another motion case to the required work.

### 3. Implement raw gyro heading propagation — 25–35 minutes

Extend `tools/analysis/analyze_imu_odom.py` rather than creating a ROS node.

AI may scaffold selecting the shared time interval, finding the nearest odometry endpoints, printing results, or plotting. You should personally implement and explain the propagation logic—roughly 20–40 lines:

```python
dt = (current_imu_timestamp_ns - previous_imu_timestamp_ns) * 1e-9
imu_heading = wrap_angle(
    imu_heading + current_angular_velocity_z * dt
)
```

Use the first odometry yaw in the comparison interval to initialize `imu_heading`. Compare only over the interval covered by both streams:

```text
start = max(first IMU timestamp, first odometry timestamp)
end   = min(last IMU timestamp, last odometry timestamp)
```

Use odometry samples nearest `start` and `end` as the reference endpoints. Skip IMU pairs with `dt <= 0`. Calculate the final error with a wrapped difference:

```python
heading_error = wrap_angle(imu_heading_final - odom_yaw_final)
```

Print at minimum:

- comparison duration in seconds;
- starting odometry yaw in radians;
- raw integrated IMU final heading in radians;
- final odometry yaw in radians;
- wrapped final heading error in radians and degrees; and
- number of IMU intervals integrated.

Also fix `compare_yaw_rate_signs()`: define a small near-zero threshold for each value separately; otherwise require both nonzero values to have the same sign. Numerical closeness and sign agreement are different questions.

Do not use the IMU's populated orientation field for the estimate. This week is specifically about propagating angular rate through time.

### 4. Observe, diagnose, measure, and explain — 15–20 minutes

Run the analyzer on the valid bag and save its exact output in the Week 8 response. Compare the observed total turn and final error with your prediction.

Write 5–7 sentences answering:

- Did the integrated heading rotate in the expected direction and by roughly the expected amount?
- What was the final wrapped error in radians and degrees?
- Is the error plausibly explained by the stationary bias measured last week, endpoint timing, transient motion, frame alignment, or some combination?
- Why does integrating a rate convert a constant bias into error that grows with time?
- Why did you anchor the initial IMU heading to odometry?
- Why is this propagation step useful even though it is worse than simply reading odometry in this simulation?
- Which measurement would provide an observation/correction if this later became a real estimator?

If the error is surprisingly large, investigate in this order:

1. units (`rad/s`, seconds, radians);
2. timestamp choice and `dt`;
3. z-axis/frame alignment;
4. sign convention;
5. inclusion of long stationary or transient portions; and
6. only then sensor noise or simulator behavior.

That ordering is part of the assignment: eliminate implementation and frame errors before blaming the sensor.
