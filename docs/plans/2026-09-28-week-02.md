# Week 2 — Close the loop on one waypoint

## Weekly goal

Extend the Nova Carter node from Week 1 so it can read its pose from `nav_msgs/msg/Odometry`, reduce the orientation quaternion to planar yaw, reason about one point across `base_link` and `odom`, and command the rover toward that point through `/cmd_vel`.

`pose in odom → goal error → desired heading → velocity command → new pose`

## This week's tasks

### 1. Extract planar pose from odometry — 20–25 minutes

In the existing odometry callback:

- Read `x` and `y` from `msg->pose.pose.position`.
- Convert `msg->pose.pose.orientation` to a single planar yaw angle. Prefer a standard tf2 helper such as `tf2::getYaw(...)`; this week is not a quaternion-math exercise.
- Print `x`, `y`, and yaw at a throttled rate so the output remains readable.
- Manually drive or rotate Nova Carter and check:
  - `x` and `y` change in the directions you expect.
  - yaw changes with rotation.
  - yaw wraps near `-π` and `+π` rather than increasing forever.

Write one sentence in a note or source comment explaining why a quaternion is present even though this controller only needs yaw.

### 2. Verify one simple 2D frame transform — 20–25 minutes

Define a point **1.0 m directly in front of `base_link`** at the moment the node starts controlling.

- Using the current `x`, `y`, and yaw, calculate that point once in the `odom` frame:
  - `goal_x = x + cos(yaw) * 1.0`
  - `goal_y = y + sin(yaw) * 1.0`
- Look up the `odom ← base_link` transform with tf2 and use it to transform the same `(1.0, 0.0)` point into `odom`.
- Print both results and confirm they are approximately equal.

Freeze the resulting `goal_x` and `goal_y`. Do **not** recompute “1 m in front” every control cycle, or the goal will keep moving away with the rover.

Before continuing, be able to say:

> `odom` is the frame in which the rover's pose and fixed goal live; `base_link` is attached to the rover and moves with it.

### 3. Add a minimal closed-loop waypoint controller — 45–60 minutes

Reuse the pose stored by the odometry callback and publish `geometry_msgs/msg/Twist` commands to Nova Carter's existing command topic.

Each control update should calculate:

- `dx = goal_x - x`
- `dy = goal_y - y`
- distance error with `hypot(dx, dy)`
- desired heading with `atan2(dy, dx)`
- heading error as desired heading minus yaw
- wrapped heading error in `[-π, π]`, for example with `atan2(sin(error), cos(error))`

Use a simple yaw-first policy:

1. If distance is below **0.15 m**, publish zero linear and angular velocity.
2. If the absolute heading error is above roughly **0.25 rad**, command angular velocity only.
3. Otherwise, command a small forward velocity and continue applying proportional angular correction.

Use modest limits, such as:

- maximum linear speed: **0.3 m/s**
- maximum angular speed: **0.6 rad/s**

The exact gains are not important. Start with obvious proportional values, clamp the outputs, and change a gain only when you can describe the behavior you are correcting.

Run the controller and observe the sequence: turn toward the goal, drive toward it, then stop inside the tolerance.

1. obtains `x`, `y`, and yaw from odometry;
2. creates and verifies a fixed goal in the `odom` frame;

A wobbly path is acceptable. A polished controller is not the objective.
