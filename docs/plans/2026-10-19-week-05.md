# Review of last week

## What went well

1. **The mission/controller separation is real, not just conceptual.** The new mission node owns goal sequencing and mission state, while the waypoint controller remains the component that turns pose error into `/cmd_vel`. The explicit states—`WAITING_FOR_SERVICE`, `READY_TO_SEND`, `WAITING_FOR_RESPONSE`, `TRACKING`, and `COMPLETE`—make the lifecycle understandable.

2. **You thought beyond the happy path.** The mission node considers service availability, asynchronous responses, arrival tolerance, timeout, controller-stop behavior, retrying, and eventually skipping a failed goal. That is useful autonomy-system thinking even though some of those mechanisms are more than Week 4 strictly required.

3. **You recognized the ROS interface limitation correctly.** Your written answer identified a ROS 2 action as a better abstraction for a long-running goal whose lifecycle includes acceptance, progress, completion, cancellation, and failure. That is the important conceptual takeaway; using a service for this learning stage is still reasonable.

## Areas to improve

1. **The main problem was scope control, not lack of technical effort.** Week 4 asked for a small two-waypoint mission layer. The submitted work also introduced a separate mission package, a shared interface package, launch/parameter plumbing, `/cmd_vel` monitoring, timeout/failure behavior, three waypoints, controller-interface migration, active-goal replacement, and controller tests. Several of those choices are technically defensible, but together they explain why the session ran well past the intended 1–2 hours. For this project, “clean enough and understood” is usually better than expanding the architecture.

2. **Be precise about autonomy-layer terminology.** The mission node currently performs **mission sequencing / goal selection**, not path planning. Likewise, the waypoint controller publishes body velocity commands; it does not directly own motor/actuator control. Those distinctions will matter much more once we move toward aircraft autonomy.

3. **The active-goal semantics are now slightly inconsistent.** The waypoint controller was changed so a new valid service request replaces an existing goal, while the mission node still contains a rejection/retry path that assumes a valid goal can be rejected. With the current controller, rejection is mostly limited to invalid coordinates, and that branch does not increment `failures_`, so a persistent rejection could retry indefinitely. This does not need to become this week's project, but the intended preemption/rejection policy should eventually be made explicit.

## What to carry forward

**Stop adding architecture for a week. Use the system you already built, measure its behavior, and practice drawing an engineering conclusion from data.**

# Week 5 — Measure one mission run

**Generated:** October 19, 2026

## Weekly goal

Record one complete Nova Carter mission and calculate one simple performance metric from the odometry:

> **Path stretch = actual distance traveled / minimum straight-line mission distance**

A value of `1.0` would mean the rover traveled exactly the straight-line distance between the start and each commanded waypoint. Values above `1.0` show extra travel caused by curved approach paths, overshoot, corrections, or other controller behavior.

This week is intentionally light on new architecture. The learning target is:

`run autonomy stack → capture data → compute a metric → interpret what it means`

## Estimated time

**60–90 minutes core**, including launching Isaac Sim, ROS setup, recording, build/runtime friction, and writing the small analysis script.

If rosbag tooling or message deserialization takes longer than expected, stop after producing a readable bag and a script that successfully iterates over odometry messages. Do not turn the assignment into another multi-hour session.

## Concrete tasks

### 1. Predict the result before measuring — 5–10 minutes

Look at the current hard-coded mission goals and write down the sequence.

At the moment the mission node queues approximately:

```text
(1.0, 1.0)
(3.0, -1.0)
(0.0, 0.0)
```

Before running anything, answer:

- Do you expect path stretch to be close to `1.0`, moderately above it, or much larger?
- What controller behavior would make the traveled distance exceed the straight-line minimum?
- Does turning in place itself add to the planar path length?

Do not calculate the answer yet. Make a prediction first.

### 2. Record one complete mission — 15–25 minutes

Run the existing waypoint controller and mission node in Isaac Sim exactly as they are.

Record at least:

```bash
ros2 bag record /chassis/odom /cmd_vel -o week5_mission
```

Let the mission run through all queued goals and reach `COMPLETE`.

Then inspect the recording:

```bash
ros2 bag info week5_mission
```

Confirm that:

- `/chassis/odom` is present;
- `/cmd_vel` is present; and
- the recording covers the full mission.

Do **not** modify the controller because the trajectory looks ugly. This week is observation before tuning.

### 3. Write a tiny offline path-length analysis — 30–40 minutes

Create a small Python script outside the ROS nodes, for example:

```text
tools/analyze_mission.py
```

It should:

1. Open the rosbag.
2. Read only `/chassis/odom`.
3. Extract each planar `x, y` sample.
4. For consecutive samples calculate:

```python
segment = hypot(x - previous_x, y - previous_y)
```

5. Accumulate the segments into **actual traveled distance**.
6. Treat the first odometry sample as the mission start.
7. Calculate the **ideal mission distance** as:

```text
start → goal 1
goal 1 → goal 2
goal 2 → goal 3
```

8. Print:

```text
Actual distance: ... m
Ideal distance:  ... m
Path stretch:    actual / ideal
```

Using AI to scaffold the `rosbag2_py` reader, serialization/deserialization calls, imports, and storage-plugin details is completely fine.

You should personally write and understand:

- how consecutive positions become a traveled-distance estimate;
- the ideal-distance calculation;
- the path-stretch formula; and
- what the resulting number does and does not tell you.

Do not turn this into a reusable analytics framework.

### 4. Interpret the number — 10–15 minutes

Write 3–5 sentences answering:

- Was the result roughly consistent with your prediction?
- What visible behavior probably contributed most to extra path length?
- Does a path stretch near `1.0` necessarily mean the controller is good?
- Would this metric still be trustworthy if the physical rover's odometry were drifting?

Save this as a short comment in the script or a small run note. No formal report is needed.
