# Week 5 — Send one goal from a mission client

**Generated:** October 19, 2026

## Weekly goal

Create a minimal C++ ROS 2 mission-client node that waits for `/goal_service`, sends **one fixed waypoint exactly once**, receives the response asynchronously, and enters a clear terminal state.

This is the first slice of the planned mission layer. It intentionally does **not** monitor odometry or sequence multiple goals yet.

The learning target is:

`wait for service → send one request → wait without duplicating it → handle response`

## Estimated time

**60–80 minutes core**, including inspecting the service, CMake edits, rebuilding, sourcing, ROS discovery, and one Isaac Sim run.

If setup or build debugging consumes the session, reaching a clean build plus a correct written explanation of the asynchronous flow is legitimate progress. Do not extend the session merely to reach the simulator.

## This week's tasks

### 1. Inspect and restate the existing service contract — 10 minutes

With the existing workspace sourced, inspect the service rather than relying on memory:

```bash
ros2 service list
ros2 service type /goal_service
ros2 interface show simple_waypoint_node/srv/Goal
```

Write down:

- request fields: `x` and `y`, in metres in `odom`;
- response fields: `success` and `message`;
- what “accepted” means: the controller has stored the goal, not that the rover has already arrived;
- why a service call can return before the physical motion finishes.

That last distinction is the main autonomy/ROS concept for this week.

### 2. Add only the mission-client scaffolding — 15–20 minutes

Add a second executable to the existing `simple_waypoint_node` package, such as `MissionNode_exe`.

The node needs only:

- a client for `/goal_service`;
- a slow timer, such as 500 ms, used to check service availability;
- one fixed goal, such as `(1.0, 0.0)`; and
- one small state variable.

AI may generate or review:

- includes and class declarations;
- ROS 2 client and timer boilerplate;
- callback signatures;
- `CMakeLists.txt` wiring; and
- explanations of compiler errors.

Do not add an odometry subscriber, waypoint container, launch-file redesign, new package, or custom interface.

### 3. Personally implement the one-request state flow — 20–25 minutes

Use a minimal state model equivalent to:

- `WAITING_FOR_SERVICE`
- `WAITING_FOR_RESPONSE`
- `ACCEPTED`
- `REJECTED`

Personally implement and understand these decisions:

1. While the service is unavailable, remain in `WAITING_FOR_SERVICE`.
2. Once it becomes available, populate one request and call `async_send_request()`.
3. Change state **before or as the request is sent** so later timer callbacks cannot submit duplicates.
4. In the response callback:
   - enter `ACCEPTED` if `success` is true;
   - enter `REJECTED` otherwise; and
   - log the returned message once.
5. In either terminal state, do nothing further.

Add concise transition logs, not a repeated timer log.

The important code to own yourself is the state transition logic and the “send exactly once” guard. It is fine if AI supplied the ordinary ROS client syntax.

### 4. Build and verify one accepted request — 15–25 minutes

Build and source the workspace, then run the existing controller and the new mission client.

Verify through logs that:

1. the mission node waits until `/goal_service` exists;
2. it sends exactly one request;
3. the controller reports the goal was accepted;
4. the mission node enters `ACCEPTED`; and
5. no additional service requests appear while Nova Carter moves.

If time remains within the core budget, run Isaac Sim and observe the rover travel to the requested point. The mission node does not need to know when it arrives yet.

### AI-use boundary

Healthy AI assistance includes ROS 2 syntax, build-system wiring, and reviewing whether the client lifetime or callback capture is safe.

You should personally own:

- why the service response means “accepted” rather than “completed”;
- every state transition;
- the duplicate-request guard;
- the goal's frame and units; and
- the explanation of why odometry and sequencing are deliberately absent.

If AI generates the entire state flow, redraw it from memory and rewrite the transitions yourself before calling the assignment complete.

- No changes to the controller or PID behavior.

## Definition of done

Week 5 is complete when:

1. `MissionNode_exe` builds and runs;
2. it waits for the service and sends one fixed `odom`-frame waypoint;
3. it cannot send a duplicate request while waiting for the response;
4. it reaches either `ACCEPTED` or `REJECTED` from the returned response; and
5. you can explain why an accepted service response does not mean the rover reached the waypoint.

A complete two-waypoint mission is explicitly **not** required this week.

## If you finish early

Add one bounded retry behavior:

- If the request is rejected, wait at least one second.
- Return to `WAITING_FOR_SERVICE`.
- Retry the **same** waypoint.
- Keep a retry counter and stop after three attempts.

Test it by manually giving the controller another goal before starting the mission client, so its first request should be rejected.

Timebox this extension to **20–25 minutes**. Do not add odometry or a second waypoint.
