# Week 3 — Make the controller's behavior intentional

**Generated:** October 5, 2026

## Weekly goal

Understand and deliberately change the controller you completed in Week 2 rather than immediately adding another autonomy subsystem.

Your current Nova Carter package already has a goal service, odometry input, proportional/PID control, angle wrapping, command limits, throttled logging, and automated tests. This week, make `heading_tolerance` affect control behavior: when the rover is badly misaligned, it should rotate without driving forward; once aligned, it may drive and steer simultaneously.

The control policy should become:

`no goal → idle`

`goal + large heading error → rotate`

`goal + aligned → drive and steer`

`inside distance tolerance → stop`

## Estimated time

**90–120 minutes core.**

Do not expand the package architecture. The intended code change is small; most of the value comes from personally tracing the existing system, writing the test, predicting the result, and validating the behavior.

## This week's tasks

### 1. Re-establish ownership of the existing control path — 20–25 minutes

Before editing anything:

1. Build the package and run the existing tests.
2. Trace one goal through these functions:
   - `initializeGoal()`
   - `odomCallback()`
   - `controlLoop()`
   - `PID::wrappedError()`
   - `PID::update()` / `PID::updateAngle()`
3. On paper or in a temporary note, write one line for each transition:

   `Goal service request → stored goal`

   `Odometry callback → stored pose`

   `Timer → distance and heading errors`

   `Errors → clamped Twist command`

   `Goal tolerance → zero command and released goal`

Pay particular attention to the current behavior: `heading_tolerance_` is reported through the `aligned` log field, but it does not currently prevent forward motion.

Do not change code until you can point to the exact lines that make the rover drive and turn at the same time.

### 2. Specify yaw-first behavior with one failing test — 20–30 minutes

Add or modify one focused controller test.

Use a goal that begins approximately **90° or 180° away** from the rover's current heading. Assert that:

- `angular.z` points in the correct direction;
- `linear.x == 0.0` while `abs(heading_error) > heading_tolerance`;
- after publishing an odometry pose aligned with the goal, `linear.x > 0.0`; and
- the command limits are still respected.

Run only that test first and confirm that it fails for the expected reason: the current controller allows forward motion while substantially misaligned.

Before continuing, explain why this is a useful failing test rather than merely changing the implementation and watching the simulator.

### 3. Implement the smallest yaw-first policy — 20–30 minutes

In `controlLoop()`, keep the existing distance calculation, wrapped heading error, angular controller, clamping, and arrival behavior.

Change only the forward-motion decision:

- If `abs(headingError) > headingTolerance_`, command zero linear velocity.
- Otherwise, use the existing linear PID output and speed limit.
- Continue producing angular correction in either case.
- Do not add a formal state-machine class or new ROS interface.

Run the focused test again, then run the entire package test suite:

```bash
colcon test --packages-select simple_waypoint_node
colcon test-result --test-result-base build/simple_waypoint_node --verbose
```

If another test fails because it explicitly expected simultaneous driving and turning, update that expectation only after explaining how the intended behavior changed.

### 4. Verify two cases in Isaac Sim — 25–35 minutes

Launch Nova Carter and send two goals through the existing `/goal_service`.

1. **Mostly ahead:** a goal with a small initial heading error.
2. **Badly misaligned:** a goal to the side or behind the rover.

For each case, watch the existing traversal log and verify:

- the distance and heading errors have sensible signs and magnitudes;
- the misaligned case initially reports `v=0` while still commanding angular velocity;
- forward velocity becomes positive after alignment;
- the rover stops and releases the goal inside the configured distance tolerance.

Do not tune the controller merely because the motion looks inelegant. Fix something only if it violates the policy above.

## What not to do

- No waypoint queue or mission executor yet.
- No EKF, sensor fusion, mapping, planning, Nav2, or obstacle avoidance.
- No tuning of integral or derivative gains.
- No PID rewrite or general-purpose state-machine framework.
- No cleanup of unrelated parameters, tf2 members, naming, or package structure.
- No new logging system; the existing diagnostic output is sufficient.

## Definition of done

Week 3 is complete when:

1. the existing test suite passes;
2. an automated test proves the rover does not drive forward while badly misaligned;
3. Nova Carter demonstrates rotate, then drive and steer, then stop in Isaac Sim; and
4. you can explain why `heading_tolerance` changes control behavior while `goal_tolerance` decides completion.

The controller does not need to take the shortest-looking or smoothest path.

## If you finish early

1. Predict what will happen if `heading_tolerance` is made much smaller, such as **0.10 rad**.
2. Run the badly misaligned goal once.
3. Compare the result with your prediction.
4. Restore the original value.

Timebox this to **15–20 minutes**. The objective is to connect a parameter to observed behavior, not to find an optimal value.
