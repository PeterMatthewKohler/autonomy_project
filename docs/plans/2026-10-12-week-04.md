## Areas to improve

1. **Use frame-accurate velocity terminology.** `cmd.linear.x` is forward or longitudinal velocity in `base_link`, not lateral velocity. This distinction will become important when the project moves to full 3D aircraft body axes.

2. **The test covers “far outside tolerance” and “perfectly aligned,” but not the threshold itself.** That is reasonable for this stage, not a production defect. Later, add cases just above and below `heading_tolerance_` so the exact boundary behavior is intentional.

3. **The repository does not record the Isaac Sim observation from the plan.** If you performed it, one or two lines noting the goals tried and observed rotate-then-drive behavior would preserve useful debugging evidence. Do not create a large report; a concise run note is enough.

## What to carry forward

# Week 4 — Sequence two waypoints with a tiny mission layer

**Generated:** October 12, 2026

## Weekly goal

Create one small C++ ROS 2 node that sends **exactly two fixed waypoints** to the existing controller in sequence.

The purpose is to learn the boundary between:

- **Mission logic:** which goal should happen next?
- **Control logic:** what velocity command will reach the active goal?

Do not change the waypoint controller this week unless you discover a genuine bug. The new mission node should use the existing `/goal_service` and observe `/chassis/odom`.

For this educational version, it is acceptable for the mission node to calculate distance to the active waypoint using the same goal tolerance as the controller. A production system would normally use a clearer result interface—often a ROS 2 action—but introducing actions now would add too much plumbing.

## Estimated time

**70–90 minutes core**, including package edits, rebuilding, ROS discovery, and simulator troubleshooting.

If environment or build friction consumes the available time, completing a mission node that successfully submits the first goal and clearly logs its state transitions is legitimate progress. Do not compensate by turning this into a long session.

## This week's tasks

### 1. Define the mission/controller boundary — 10 minutes

Before coding, write down the ownership split:

- Mission node owns a two-element waypoint list, the current waypoint index, and when to request the next goal.
- Waypoint controller owns pose-error calculation, yaw-first behavior, velocity commands, and stopping at the active goal.
- Both currently interpret waypoint coordinates in `odom`.
- The mission node observes odometry only to decide when to advance; it does not publish `/cmd_vel`.

Use two simple waypoints with no obstacles, for example:

```text
(1.0, 0.0)
(1.0, 1.0)
```

### 2. Add minimal ROS 2 scaffolding — 15–20 minutes

Add a second executable to the existing `simple_waypoint_node` package, such as `MissionNode_exe`.

The node needs only:

- a client for `/goal_service`;
- a subscription to `/chassis/odom`;
- a short periodic timer for service availability and retries;
- a hard-coded two-waypoint container;
- a current waypoint index; and
- a small mission state variable.

Using AI for includes, class declarations, CMake wiring, callback signatures, and ordinary ROS 2 client boilerplate is acceptable. Read enough of that scaffolding to know where the request is sent, where the response arrives, and which callback changes mission state.

Do not add a new package, launch framework, configuration format, or custom interface.

### 3. Personally implement the mission state transitions — 30–35 minutes

Use a deliberately small state model. Names may differ, but the behavior should be equivalent to:

- `WAITING_FOR_SERVICE`: wait until `/goal_service` is available.
- `READY_TO_SEND`: send the current waypoint once.
- `WAITING_FOR_RESPONSE`: do not send duplicate requests.
- `TRACKING`: after the controller accepts the goal, monitor distance to it.
- `COMPLETE`: stop sending requests after the second waypoint.

Personally write and understand:

- the waypoint container and index;
- `dx`, `dy`, and Euclidean distance to the active waypoint;
- the transition from accepted request to `TRACKING`;
- the arrival condition using the configured tolerance;
- incrementing the index without running past the container; and
- retry behavior if a service request is rejected because the previous goal has not quite been released yet.

Keep all coordinates and distances in metres and in the `odom` frame.

Add one concise log at each state transition. Avoid continuous high-rate logging.

### 4. Build and run one two-waypoint mission — 15–25 minutes

Build and source the workspace, launch the existing controller and the new mission node, then start Isaac Sim.

Verify that:

1. the first goal is accepted without a manual service call;
2. Nova Carter reaches and stops at the first waypoint;
3. the mission node advances and submits the second waypoint;
4. Nova Carter reaches the second waypoint; and
5. the mission node reports completion and sends no more requests.

If the second request is briefly rejected, confirm that the node returns to a retryable state rather than skipping the waypoint or flooding the service.

No new automated test is required in the core assignment this week. The asynchronous client and simulator integration are enough new surface area for one session.
